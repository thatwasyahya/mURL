One identifier that opens a whole working context.

A URL addresses one resource. An mURL addresses a set of them — a repository, its docs, its dashboard, a working directory, a terminal — under a single name that can be inspected before anything happens.

  • experimental
  • format v0.2
  • release 0.4.0
  • Rust · MIT OR Apache-2.0

This is a proposal with a working implementation, not a standard. The murl scheme is unregistered, no third party has adopted it, and the format may still change before 1.0. Read it as a design worth arguing with — see the specification page for what that means in practice.

The idea in two lines

URL   :  identifier ──────────────▶ one resource
mURL  :  identifier ──▶ manifest ──▶ { resource, resource, resource, … }

The indirection through a manifest is the whole point. Because the set is a document rather than a string, it has a canonical byte form — so it can be hashed, signed, versioned, cached, diffed, and above all shown to you before it acts. An mURL is a name, never a container.

What resolution looks like

A manifest

Publishing a namespace means serving static JSON from a web server under /.well-known/murl/. There is no registry, no account, and no new infrastructure. 

{
  "murlVersion": "0.2",
  "id": "murl://local/project-x",
  "name": "Project X",
  "resources": [
    { "id": "source",    "kind": "https",    "target": "https://github.com/acme/project-x" },
    { "id": "workspace", "kind": "dir",      "target": "~/projects/project-x" },
    { "id": "term",      "kind": "terminal", "target": "~/projects/project-x", "dependsOn": ["workspace"] }
  ]
}

Resources may also be file, a nested murl, or a custom:* kind dispatched through a handler you registered yourself. Full schema in specification §5.

Three tiers, decided locally

An identifier that can make an operating system open many things is an attack primitive by default. Classification derives from what a resource is — its kind plus its target — never from what a manifest claims about itself.

SAFE

https

Rendered by a sandboxed browser. Worst case is roughly a tab.

SENSITIVE

file, dir

Exposes or touches local data. Prompts, always, with the path shown.

DANGEROUS

terminal, custom:*, executable-ish files

Opening it is, or is one dialog from, code execution. From an untrusted manifest this is a refusal — not a prompt.

That last rule is the keystone. Users can be talked into one click, and one click is exactly what a hostile mURL gets; making terminals from unknown senders un-clickable removes the social-engineering path rather than warning about it. More on the security model →

Try it

There is no published package yet. Build from source — the workspace is four Rust crates with no unsafe code. 

git clone https://github.com/thatwasyahya/mURL && cd mURL
cargo build

# a hermetic guided tour: temp state, dry-run open, auto-cleanup
bash examples/demo.sh

Or drive it by hand:

murl create --name "Project X"                # write a starter manifest
murl validate project-x.murl.json
murl name add project-x project-x.murl.json   # install as murl://local/project-x

murl resolve murl://local/project-x           # see the full plan — nothing opens
murl open murl://local/project-x              # consent, then dispatch
murl open 'murl://local/project-x#workspace'  # just one part of it

murl keygen && murl sign project-x.murl.json  # sign it
murl os install                               # make murl:// clickable

murl resolve before murl open is the habit worth forming: it prints the fully resolved plan, every tier, and the trust status of the manifest, without dispatching anything.
